# ADR 0001 - Use the system's Python 3.14

- **Status:** accepted
- **Date:** 2026-08-11

## Context

The development environment has a single interpreter installed: CPython
**3.14.7**, via the system installer (not a `uv`-managed one).

The "safe by habit" option was to pin Python 3.12 and let `uv` download a
managed interpreter, assuming the ecosystem didn't yet support 3.14. Before
deciding, it was checked package by package whether that assumption still held.

## Decision

Use the system's Python 3.14. In `pyproject.toml`:

```toml
requires-python = ">=3.14"

[tool.uv]
python-preference = "system"
```

and `.python-version` pinned to `3.14` with `uv python pin 3.14`.

`python-preference = "system"` is necessary: by default `uv` prefers its own
managed interpreters and would download one even if a compatible one is already
installed.

## Justification

Every critical dependency publishes wheels for CPython 3.14:

| Package | Version | Note |
|---|---|---|
| SQLAlchemy | 2.0.51+ (Jun 2026) | `cp314` wheels for Windows, macOS, and Linux |
| psycopg | 3.3.4 (May 2026) | explicit 3.14 support |
| mypy | 2.3.0 (Jul 2026) | `cp314` wheels |
| FastAPI, pydantic, pytest, uvicorn | current | 3.14 wheels available |

Reproducible verification after `uv sync`:

```
$ uv run python -c "import sys; print(sys.version)"
3.14.7 (tags/v3.14.7:823f032, Aug  5 2026, 10:51:32) [MSC v.1944 64 bit (AMD64)]

$ cat .venv/pyvenv.cfg
home = <system Python 3.14 install path>
```

`home` points to the system interpreter: `uv` did **not** download one.

## Consequences

- One less setup item to explain and one less thing that can fail on another
  machine.
- If some future new dependency doesn't publish `cp314` wheels, it will need
  to be compiled or waited on; the risk is accepted and will be revisited when
  adding dependencies.
- CI must use the same version (`3.14`) so local and remote don't diverge.
